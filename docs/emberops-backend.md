# EmberOps back end

Hearth runs in one of two modes, chosen by one setting.

- `postgres` (the default): standalone. Everything lives in Hearth's own Postgres, as it always has. Nothing in this document applies and behaviour is unchanged.
- `emberops`: operational data lives in EmberOps (on Frappe) and Hearth is a front end for it, over the Frappe REST API and the `emberops_hearth` addon. What EmberOps does not model stays in Hearth's Postgres.

Status: every domain the `emberops_hearth` addon maps is wired, tested against a fake Frappe site (`internal/emberops/fake`) and, since 2026-11-20, run against a real EmberOps site: a copy of the production image on its own MariaDB, filled from Fireball's nightly Hearth backup, with a scratch Vord realm for sign in. That run is where the fixes under "What a real site taught us" came from. Three kinds of domain exist, and the table under "What lives where" says which each one is: served from EmberOps (no Postgres row), served from EmberOps with a Postgres spine (the ids and indexes Hearth's files, comments, links, search and access control hang off), and kept in Postgres with a copy written to EmberOps on every change (where Hearth's access control reads the data on every page).

## Configuration

| Variable | Meaning |
|---|---|
| `HEARTH_BACKEND` | `postgres` (default) or `emberops`. Anything else fails at startup. |
| `HEARTH_EMBEROPS_URL` | Site root, e.g. `https://ops.example.com`. Required with `emberops`; https in production. |
| `HEARTH_EMBEROPS_CLIENT_ID`, `HEARTH_EMBEROPS_CLIENT_SECRET` | Vord service client (client credentials). Required with `emberops`: importers, rules and scheduled work have no signed-in person. |
| `HEARTH_EMBEROPS_AUDIENCE` | Audience a person's Vord token must carry for EmberOps. Default `emberops`. Must not be the browser login's client id. |
| `HEARTH_EMBEROPS_TIMEZONE` | The EmberOps site's time zone (IANA). Frappe stores naive local datetimes; Hearth converts. Default `UTC`. Set it to the site's System Settings time zone. |
| `HEARTH_EMBEROPS_CACHE_TTL` | Shared cache for slow-changing reads (people, property defs). Default `5s`, at most `1m`, `0` turns it off. |
| `HEARTH_EMBEROPS_CURRENCY_PER_CENT` | The value of one cent in the site's currency. Hearth keeps money in cents (pay rates, part costs), EmberOps in currency units. Default `0.01` (dollars). Use the same value as `hearthctl emberops-migrate --currency-unit`. |

Startup fails, naming every problem, when: the back end is unknown; `emberops` is set without a URL or without the service client; `emberops` is set without single sign-on (`HEARTH_OIDC_*`) or without `HEARTH_ENCRYPTION_KEY`; any `HEARTH_EMBEROPS_*` URL or client setting is present while the back end is `postgres` (someone believes the switch is made and it is not).

## What lives where

"EmberOps" means the record is only there. "Spine" means a Postgres row stays for the ids and indexes the doc lists. "Copy" means Postgres stays the store and every change is also written to EmberOps.

| Data | `postgres` | `emberops` |
|---|---|---|
| Tasks, work orders, assets, purchase orders; docs, wiki, notes, templates, daily reports | Postgres | EmberOps holds title, body, status, priority, due, started, completed, assignees and checklist; the spine holds the id, space, parent, files, comments, links, grants, versions and the search index. EmberOps-side edits are copied into the spine on read (see below) |
| Saved views | Postgres | EmberOps (`Hearth View`) |
| Time off requests | Postgres | EmberOps (`Hearth Time Off Request`, or Leave Application with HRMS) |
| Time entries, running timers, time tags, approvals | Postgres | EmberOps (`Timesheet Detail` in the person's day Timesheet, `Hearth Timer`, `Activity Type`). No spine. Who may approve whose time is still Hearth's structure; pay rates are Activity Costs |
| Capacity | Postgres | EmberOps (`Employee.hearth_minutes_per_week`) |
| Maintenance plans and their occurrences | Postgres, generated by Hearth | EmberOps (`Maintenance Plan`; an occurrence is the work order CMMS generated). **CMMS generates the work orders. Hearth's own generator is not registered in this mode** and "Raise now" is refused |
| Meter readings | Postgres | EmberOps (`Hearth Meter Reading`) |
| Downtime | Postgres | EmberOps (`Asset Failure Log`, left a draft) |
| Asset code, parent, installed and retired dates | Postgres | Written to the spine (it enforces unique codes and cycles) and to the Asset; read from the Asset. The asset tree and its rollup columns are still the spine's (see "Remaining") |
| Rules and rule runs | Postgres | EmberOps (`Hearth Rule`, `Hearth Rule Run`). The engine still runs in Hearth on Hearth's own events (the outbox) and reads and writes rules and runs there. A real run is unique per rule and event |
| Calendar events | Postgres | EmberOps (`Event`). Feed tokens and cached Google events stay in Postgres |
| Companies, contacts | Postgres, with Hearth grants | EmberOps (`Customer` or `Supplier`, `Contact`). **Hearth grants no longer apply to them**: EmberOps roles decide who sees them |
| Parts and stock movements | Postgres | EmberOps (`Item`, `Stock Entry`, submitted so stock moves; removing a movement cancels it) |
| Teams | Postgres | **Copy.** Postgres stays the store because a team is a grant subject read by authz on every page; each change is written to an `Employee Group` |
| Spaces, space managers and department members, space grants | Postgres | **Copy.** Postgres decides access (a query on every page). The tree, members, managers and grants are written to `Hearth Space` after every change so the addon's permission hooks compute the same access (see "Spaces and access") |
| Department requests | Postgres | **Copy.** Approving changes the person's departments, which authz reads; each request is written to `Hearth Department Request` |
| Canvases | Postgres | **Copy.** Access and the live card lookups are Hearth's; each canvas is written to a `Hearth Document` of kind canvas with the graph in `content` |
| Property definitions, property values, entity links | Postgres | **Copy.** Views and searches filter and join on them in SQL; values ride in the document's properties JSON, definitions become `Hearth Property Def`, links `Hearth Entity Link` (id derived from the relationship) |
| Capability grants, approver | Postgres | Postgres (Hearth's own access control) |
| Channels, messages, mail, inbound addresses, calls | Postgres | Postgres (not in the addon) |
| Notification preferences, offline queue, playgrounds, calendar feed tokens, Google connections | Postgres | Postgres (not in the addon) |
| Sessions, local credentials, user identities, API and agent tokens | Postgres | Postgres. Sessions also hold the person's Vord tokens, sealed |
| Search index | Postgres full text, OpenSearch if configured | The same. OpenSearch stays the index in both modes |
| Audit log, outbox, jobs | Postgres | Postgres |
| Files | Object store | Object store |

## How a document is stored in `emberops` mode

A document is more than its fields. Hearth's files, comments, links, grants, versions, time entries and search index all hang off the document id, and they do not move. So a document keeps a spine row in Postgres, and the operational record is projected into EmberOps beside it.

Writes go to Postgres first, which keeps Hearth's own rules exactly as they are (access checks, versions, events, search indexing), and then to EmberOps as the signed-in person, which applies EmberOps's permissions and validation. If EmberOps refuses a create, the spine row is removed again. If it refuses an update, the error is returned and the spine is one write ahead until the next save.

Because the spine write is the ordinary Postgres write, the outbox events fire as before and OpenSearch is fed from the same path in both modes.

Reads take every field the addon stores from EmberOps, one batched call per doctype per page (`hearth_id in (...)`): the title everywhere, the body when a single document is opened, and for tasks and work orders the status, priority, due, started and completed dates and the assignees. So an edit made in EmberOps is what Hearth shows. The space and the parent stay the spine's, because Hearth's access control is computed from them.

Ids: every EmberOps record carries the Hearth uuid in `hearth_id` (`api.upsert` and `bulk_upsert` key on it), so ids are identical in both modes and a switch in either direction keeps every link, URL and bookmark.

Edits made in EmberOps reach the spine on read. Hearth records, in `emberops_doc_sync` (migration 00047), the EmberOps `modified` stamp it last wrote or read for each document. A page whose records carry a different stamp was edited in EmberOps: the changed fields are copied into the spine as a new version (author: whoever EmberOps says made the edit, else the document's owner), with the same outbox events an ordinary edit raises, so search and rules see it. A stamp that moved without any change Hearth shows (a comment on the record) copies nothing and mints no version. The work is bounded and batched: one query for the marks of the page, one fetch for the bodies of the records that changed, and at most 25 documents written per read (the rest follow on later reads, and the page shows EmberOps's state regardless). Documents never compared before (the migration wrote them) take EmberOps's current stamp as their baseline. Soft deletes, space and parent changes made in EmberOps are not followed.

A status change on a task reaches its open subtasks at any depth, in either mode and from either side. Hearth does it in the same transaction as the parent's write (`docs.cascadeStatus`) and sends each moved subtask to EmberOps as the service client. EmberOps does it in the `emberops_hearth` addon's Task hook for an edit made directly in EmberOps (the addon's README says how the two never loop); Hearth then copies the parent's change on read and its own cascade finds the subtasks already moved. Done and cancelled subtasks keep their status whatever the parent becomes, and a subtask's change never reaches its parent. Each subtask Hearth moves gets an audit row (`task.close_with_parent`, kept as the name for every status) naming the parent and the status, and a running timer on a subtask is left running, as when a person changes the task by hand.

Checklist ticks and removals are sent to EmberOps at once, like any other edit.

Where the seam is: each domain package declares a `Store` interface (`internal/<domain>/store.go`) that its Postgres `*Service` implements unchanged, and the server holds `Store`s. `internal/emberops/stores` provides a `Set` of stores: `stores.Postgres(...)` is the default, `stores.EmberOps(...)` swaps in the EmberOps ones. An EmberOps store embeds the Postgres store and overrides what it serves, so a method it does not override still works against Postgres. `internal/architecture_test.go` is untouched and green.

## Authentication and Vord

Sign-in is unchanged: people sign in to Hearth with Vord OIDC exactly as today. In `emberops` mode three things are added.

1. The sign-in also requests the client scope named by `HEARTH_EMBEROPS_AUDIENCE` (default `emberops`), so the access token carries that audience.
2. The access and refresh tokens from the sign-in are kept server-side, sealed with `HEARTH_ENCRYPTION_KEY` and bound to the session id, in `sessions.vord_tokens` (migration 00045). They never reach the browser. The access token is refreshed with the refresh token when it has less than 60 seconds left, under a row lock so two requests or replicas do not both spend a rotating refresh token. A 401 from EmberOps invalidates the token once and retries. If the Vord session behind it has ended, the call fails with `auth.ErrTokenExpired`, and the web layer answers the request that hit it by ending the Hearth session and sending a browser to `/login?next=<the page they wanted>` (an HTMX request gets `HX-Redirect`, the JSON API a `401` with a JSON body). The same for `auth.ErrNoUserToken`. Only a request that was about to answer with an error status is rewritten; a handler that swallows the error and renders anyway is not caught. A session with no token (a local password sign-in, or one that began before the switch) fails with `auth.ErrNoUserToken` rather than borrowing anyone else's identity.
3. Each EmberOps call carries `Authorization: Bearer <that person's access token>`, so EmberOps's own permissions (roles, the addon's space rules) decide what they may do.

Background work with no person (importers, the rules engine, scheduled jobs) uses a Vord client-credentials token for the service client, cached until 30 seconds before it expires. EmberOps maps that service account to a Frappe service user.

Vord settings to make:

- Client scope `emberops` with an Audience mapper whose included client audience is `emberops`, attached to Hearth's login client as an optional scope. (Alternatively give the login client roles from the `emberops` client, which makes Keycloak add the audience by itself. Either way the token's `aud` must contain `emberops`.) The same scope on the service client.
- A service client for Hearth (for example `hearth-service`), confidential, service accounts on. Its credentials are `HEARTH_EMBEROPS_CLIENT_ID` and `_SECRET`.
- The `emberops_vord` addon's `site_config.json` `vord` block on the EmberOps site: `client_id` `emberops`; if `allowed_azp` is set, include Hearth's login client id and the service client id; `service_users` mapping the service account (`service-account-hearth-service`) to a Frappe user that holds the `Hearth Admin` role; and the client roles each person needs. Bearer auth is on by default whenever `realm_url` is set.

Hearth's own authorization still gates its UI as today. In this mode the permission that matters for data is EmberOps's: Hearth may show a button EmberOps will then refuse, and it reports the refusal.

## Spaces and access

Hearth's access control stays a query on its own tables (grants, space managers, department membership). EmberOps gets a copy so the addon's `permission_query_conditions` and `has_permission` hooks decide on the same facts. `stores.SpaceSync` writes every space with its parent, kind, order, `is_department`, its managers and department members (`members` rows) and its grants (`grants` rows: a person becomes a `User` row, a team an `Employee Group`, "everyone in the org" the `Employee` role; a grant to a channel has no EmberOps subject and is left out). It runs inline after a space edit, in the background (debounced to 2 seconds) after any other write by a signed-in person, since people are moved between departments and grants made from many pages, and every five minutes. A copy that has not changed since the last send costs no call. A space deleted in Hearth is deleted in EmberOps. The migration builds spaces with the same function.

Differences to know about: Frappe has no comment-only level, and the addon collapses levels to read and write; an expiring grant is sent with its expiry and dropped from the copy once it has expired, at the next sync.

## Performance

Lists are one call with `fields` and `filters` (never a get per row). People and linked-record names are resolved with one directory read and one `name in (...)` read per page. Each request carries a memo, so asking for the same thing twice asks EmberOps once, and any write empties it. Slow-changing reference reads (the people directory) share a short cache (`HEARTH_EMBEROPS_CACHE_TTL`), emptied by any write through the same client. Reads retry transient failures (429, 502 to 504) with backoff; writes never retry.

Pages that need Frappe realtime later: the task board, the inbox badge and the time approval queue are polled today. Frappe's socketio events (`doc_events` on Task, Timesheet, Hearth Time Off Request) are the way to make them live; Hearth would subscribe per person with the same Vord token. Not built.

## Rollout

1. Install `emberops_hearth` on the EmberOps site and fill Hearth Settings (company, default asset item, category, location, Activity Type). Make the Vord changes above.
2. Take a backup: `hearthctl backup`. Switching back relies on it.
3. Set the new environment on a shell or Job that can reach both Postgres and EmberOps: `HEARTH_BACKEND=emberops`, the `HEARTH_EMBEROPS_*` settings (including `HEARTH_EMBEROPS_CURRENCY_PER_CENT` if the site is not in dollars), `HEARTH_OIDC_*` and `HEARTH_ENCRYPTION_KEY`. The running server keeps its old environment.
4. Dry run: `hearthctl emberops-migrate --dry-run`. It reads and maps every table and writes nothing to either side, and it needs no network to EmberOps. Read the report: rows Hearth holds, rows mapped, rows skipped and why (a principal with no email address has no User; a link to a file has no EmberOps equivalent).
5. Run it: `hearthctl emberops-migrate`. It follows the addon's migration order, writes each record with `bulk_upsert` keyed by `hearth_id` (200 per request, at most 500), and checkpoints each step in `emberops_migration`. It is idempotent: running it again updates what it wrote and duplicates nothing. It is resumable: a run that stops continues from the last finished page. Records EmberOps refused are counted and listed; fix the cause and run again with `--restart`. `--only tasks,work orders` limits it to named steps. Time entries go through `upsert_time_entry`, which files each into its employee's timesheet for the day; running timers become `Hearth Timer`s.
6. Verify: the report ends with, per step, what Hearth mapped and how many records EmberOps now holds with a `hearth_id`. They should agree. Spot check a task and a work order in EmberOps.
7. Switch: deploy the server with the new environment. The startup log says `storage back end: emberops`. Sign in again (sessions that began before the switch carry no Vord token).
8. Run the migration once more just before or after the cut-over to carry anything written in between; it is cheap.

In this mode the server does not register Hearth's PM generator, so there is no second source of occurrences once CMMS runs. Before the cut-over, make sure each Maintenance Plan's next due date in EmberOps is right, since CMMS now owns it.

Things the migration does not carry: rule run history (`Hearth Rule Run`); the draft Stock Entries it writes are not submitted, so stock on hand in EmberOps starts from the site's own counts; principals with no email address (bots and agents with no mailbox) become no User; capacity rates (`Activity Cost`) are not written; links to files and channels; document grants (Frappe DocShare) and guest links; version history (Frappe keeps its own from the first write).

## Rollback

Postgres still holds the spine of every document and everything not in the table above, so rolling back is deploying with `HEARTH_BACKEND=postgres` (and the `HEARTH_EMBEROPS_*` variables removed, which the validation insists on). Limits:

- Saved views, time off requests, time entries and timers, maintenance plans, meter readings, downtime, rules and rule runs, calendar events, companies, contacts, parts and stock movements are EmberOps-only in this mode. Rows created after the switch exist only in EmberOps. Copying them back is not built; until it is, take a backup of them from EmberOps before rolling back if they matter. (Teams, spaces and their access, department requests, canvases, property values and definitions and links are Postgres in both modes, so they roll back intact.)
- Rolling back turns Hearth's PM generator back on; make sure CMMS's scheduler is off or paused first, or both will raise occurrences.
- Task, work order, asset and document fields changed inside EmberOps (not through Hearth) are not in Postgres, so they revert to the last value Hearth wrote.
- `sessions.vord_tokens` is ignored by the standalone build.
- Hearth uuids are the same in both, so nothing needs re-linking.

## Remaining

- The asset tree's rollup columns (open work, minutes, parts cost, downtime per asset and subtree) are recomputed from EmberOps (`stores/plantrollup.go`): the tree and who sees what are the spine's, the numbers are EmberOps's. Labour cost is zero in both modes, because a person's rate is an Activity Cost the migration does not write.
- `Imported`, `Reassign` and `DeleteImported` time entries work, but a reassigned entry is written again under the new person with a new id, because a Timesheet row cannot change Timesheet.
- A timer can be started against a task or a work order only (`Hearth Timer` has no other link); a timer started on another kind of document is unattached.
- Companies and contacts lose Hearth's per-record grants (see the table). Customer and Supplier are different documents, so a company cannot change between customer and vendor.
- A department manager deleting someone else's calendar event is refused unless EmberOps allows it.
- Tag rename renames the Activity Type, but entries already tagged keep the old text until edited.
- Property values, Employee Group membership, Department Request status and canvas content edited inside EmberOps do not flow back.
- `hearthctl daily-report` and `hearthctl time-import` go through the same stores as the server (`cmd/hearthctl/backend.go`): with `HEARTH_BACKEND=emberops` (and the `HEARTH_EMBEROPS_*` and `HEARTH_OIDC_*` settings in the Job's environment) their rows land in EmberOps, using the service client.
- Agents, the MCP server and the playground build their own services from the Postgres ones, so what they read of the domains above is the spine, not EmberOps.

## What a real site taught us

The first migration of Fireball's whole database into a real EmberOps site (2026-11-20) refused 5314 of 5880 records. Every refusal was something the fake site could not show, and each is fixed in code, in `emberops_hearth` unless it says Hearth:

- ERPNext will not make an Employee without a gender, a birth date and a joining date, none of which Hearth knows. Nobody got an Employee, and so every team, time entry, time off request and department request that named a person was refused (941 time entries alone). The three fields are optional now (Property Setters).
- The service account could not make a User, an Item, an Asset or an Employee Group, and could not share a work order with the person it was assigned to. `api.upsert` now makes a person's User itself, only for a caller holding Hearth Admin and with no role, user type or module field passed through, and Hearth Admin holds exactly the Custom DocPerms the back end writes with (`spec.HEARTH_ADMIN_PERMISSIONS`, no User). Roles for a person come from Vord at sign in.
- ERPNext refuses an open task under a completed parent and a task that ends after its parent. Hearth has neither rule (113 of 2161 tasks). The parent is set aside for ERPNext's checks and put back, the planned end date is held to the parent's, and the real due date stays in `hearth_due_at`.
- Hearth parts are Items in the group "Spare Parts", which stock ERPNext does not have, and assets need an item, a category and a location that Hearth Settings named and nothing made. Install and every migrate make them (`defaults.ensure_catalog_defaults`).
- The assets step read only assets that had an `asset_fields` row and never found a root, so it carried none of Fireball's 34, and every plan, work order, meter reading and downtime row that named one was refused. It reads every asset document, deleted ones too.
- A migrated company or contact would have made a Customer or Supplier of every one of 6668 companies, prospects included, beside the ones the CRM sync projects. The two steps run only when `HEARTH_EMBEROPS_CRM_PARTIES=emberops`.
- A page of 200 tasks takes a real site longer than the live client's 30 seconds. The migration waits 15 minutes for a call.
- The report listed five lines a step and the skips came first, so no refusal showed. It now counts every refusal by cause, with ids and numbers taken out, and the addon says why when Frappe leaves it in the message log.
- A page of 500 Hearth ids is 20,000 bytes of query string and EmberOps's web server refuses a request line over 4094 bytes, so the tasks and documents pages were a 500. Reads that long go in a POST body.
- ERPNext keeps an item's reorder level in a child table a list cannot ask for, so the parts page was a 500. It has its own field, `hearth_reorder_at`.
- Assignees piled up as new ToDos on every save of a finished or cancelled task (4409 extra after nine runs). They are reopened now.
- Staff reach EmberOps's Hearth records at `/app/hearth`, a workspace the addon ships.
- A person who signs in with Vord holds the roles in their token. Every member of staff holds the realm role `fireball-staff` and no EmberOps client role, so the site grants roles by realm role (`realm_role_grants` in the `vord` block of `site_config.json`, set in `embernet-iac` `emberops.tf`).

## Verify before relying on it

- The migration's SQL is exercised only by `internal/emberops/migrate/pg_integration_test.go`, which needs `TEST_DATABASE_URL` and was not run. Run it, and run `--dry-run` against a copy of production, before the real thing.
- Run against a real site on 2026-11-20 (see "What a real site taught us"): everything that mattered differed from the fake, and the fixes are in. Still to prove on the live site, because the scratch one is not it: the Hearth workspace opens from EmberOps's sidebar, the Vord realm role grants reach a real staff token, and the setup Job applies the Property Setters and Custom DocPerms on the live database.  Not exercised even there: `PUT docstatus=1` as the way a Stock Entry is submitted, `frappe.client.rename_doc` for tag renames, and `week_load`.
- Link fields that Hearth reads back (a task's space, a view's space) come back as Frappe names and are mapped to Hearth ids with a `name in (...)` read. A record made in EmberOps itself has no `hearth_id` and maps to its Frappe name.

## Tests

`go test ./internal/emberops/... ./internal/auth ./internal/platform/config` run without a database: the client against a fake Frappe (token forwarding, service token, 401 retry, memo, cache, error mapping, bulk batching), session token refresh, the redirect on an ended Vord session, every store (documents and their sync into the spine, time, maintenance, plant and downtime, space sync, rules, calendar, teams, department requests, canvases, properties and links, CRM), the mapping against the addon's, the migration (dry run, order, idempotency, resume), and config validation. Each store test also asserts how many calls a page makes. The Postgres-backed suites skip without `TEST_DATABASE_URL`, as before.
